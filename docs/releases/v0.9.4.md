## What's new in 0.9.4

A security release for the clipboard in session tabs, from the Omarchy plugin marketplace's review (omacom/omarchy-plugin-marketplace#11850). Everything else is unchanged from 0.9.3.

- **A session tab no longer reads the clipboard through Qt.** Each time a tab got the keyboard, and on every clipboard change while it had it, the window read the clipboard with Qt's own reader: in the window's main thread, with no time or size limit. Any app holding the clipboard could freeze OMARemote's window or fill its memory. Tabs now read it the way text fields have since 0.7.0: `wl-paste` in a process of its own, at most 1 MiB, at most 2 seconds, while the window keeps running. Text that is larger or slower is not passed on.
- **Clipboard switched off means untouched.** A tab whose connection has *Clipboard* off no longer reads your clipboard at all, and no longer sets it from the session. Gliff tabs never read it from the window: Gliff's session process shares the clipboard itself, within its own limits, only while the tab has the keyboard.
- **VNC now follows the Clipboard switch.** The switch had no effect on VNC connections: the clipboard was shared either way. It now stays local when the switch is off.
- **Text from a server is kept to 1 MiB** before it reaches your clipboard, for RDP, VNC and SSH (a program's OSC 52 copy, e.g. from tmux or Neovim); larger text is dropped whole, not cut.

## Security review

Reviewed everything since 0.9.3 against `docs/security-review.md`, with the clipboard in both directions as the focus: every place the window reads it (session tabs, text fields; no other reader is left, and a new test fails if Qt's `QClipboard::text()` or `mimeData()` returns to the plugin), every place a session sets it (RDP, VNC, SSH, Gliff), and what the Clipboard switch reaches in each. Found and fixed: the unbounded read reported in #11850, the read with the switch off, the unbounded text from a server, and VNC ignoring the switch; each has a test that fails on 0.9.3. Checked and unchanged: RDP's clipboard channel is only opened when the switch is on (FreeRDP's `-clipboard`), and Gliff's clipboard was already bounded (32 MiB an item, transfers in chunks, focus only).

Left as is: SSH connections have no Clipboard switch; a program on the server can still put text on your clipboard with OSC 52 (now at most 1 MiB), and reading your clipboard is never offered to it.
