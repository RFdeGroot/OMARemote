## What's new in 0.9.5

A security release for the remote cursor in session tabs, from the Omarchy plugin marketplace's review (omacom/omarchy-plugin-marketplace#11853). Everything else is unchanged from 0.9.4.

- **A server can no longer fill OMARemote's memory with cursor shapes.** The window kept every cursor shape a session ever sent, for as long as the tab was open. A VNC server gave each new shape a new number, so sending shapes over and over grew the window's memory without end; RDP sessions grew it too, because the window was never told when the server dropped a pointer. The window now keeps at most 64 shapes and forgets the one used longest ago first, for every protocol.
- **Cursors are at most 512 × 512 pixels.** The window checked a cursor's size by multiplying width and height in 32 bits: a large enough size wrapped around and passed the check with a few bytes of picture, so the window would read far past them. The size is now checked in 64 bits, and a cursor wider or taller than 512 pixels is refused before anything is decoded. The same limit holds in each session process before it passes a cursor on: VNC (whose own loop over the cursor's pixels could overflow too), RDP (large pointers go up to 384 × 384) and Gliff (was 1024 × 1024). A refused cursor is not shown; the previous one stays.
- **A VNC server that stops in the middle of a message no longer holds the session.** The VNC session process waited for the rest of the message forever, without even reacting to being stopped (Stop ended it after 3 seconds by force). A read now gives up after 30 seconds and the session ends with "The connection was lost". An idle session is not affected: waiting for the next message is not a read.

## Security review

Reviewed everything since 0.9.4 against `docs/security-review.md`, with what a malicious server can make the window and the session processes hold as the focus: every path a cursor takes (VNC `got_cursor`, RDP `pointer_new`, Gliff `cursor_shape`, the window's `cursor` and `cursor-set` lines), the size checks on each, and how many shapes are kept. Found and fixed: the unbounded cache reported in #11853, the size check that overflowed in the window and in the VNC session process, and RDP pointers kept after the server freed them; while testing the fix, a VNC server stalling mid-message held the VNC session process. Each has a test that fails on 0.9.4 (tests/test_clipboard.py for the cursors, the new tests/test_vnc.py against a fake VNC server).

Left as is: libvncclient, the VNC library, allocates room for a cursor of the size the server announces (at most 65535 × 65535) before OMARemote's session process sees it and refuses it. That memory belongs to the session process of that one connection, not to OMARemote's window, and it is only filled as fast as the server actually sends the pixels.
